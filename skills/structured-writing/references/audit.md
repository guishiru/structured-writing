# 审模式：诊断现有稿件

> 何时读：用户给了现成稿子，问「怎么样」「有什么问题」「帮我看看」，或分享草稿未明确要求。

**第一条也是最重要的一条：审的时候不改写。**

返回诊断，不返回新稿。用户看完说「按你说的改」，才切到 `revise.md`。
擅自重写别人的文字，等于把一次评审变成一次夺权。

---

## 前置：两个必须先确定的事

### 1. 读者是谁

审之前必须知道**这份文档是写给谁、要解决他什么问题**。

- 用户说了 → 用他说的
- 用户没说 → 从文档本身推断，并在报告的【场景判断】段里标注「（推断）」
- 推断不出来 → 这本身就是第一条发现：文档没有明确的目标读者

同一份稿子给老板看和给同级看，合理的结构是不一样的。不知道读者就别评结构。

### 2. 属于四类场景中的哪一类

查 `scenarios.md` 判定，并在报告第一段写出来。这一步决定了后面用什么标准衡量：

- 判成「**准确总结工作**」→ 按**自下而上**衡量：有没有做「概括总结」这一步？
  写的是动作还是结果？
- 判成「**充分说服他人**」→ 按**自上而下**衡量：观点是不是开门见山？
  有没有主动回答反对意见？
- 判成「**有力汇报方案**」→ 有没有给出**选项**？只给一个方案的，其实是「说服」不是「汇报方案」

**场景判错，后面的诊断全部失准。** 例如把周报判成「清晰传递信息」，
就不会去查它有没有归纳结论，而那恰恰是周报最常缺的一环。

---

## 诊断四步

1. **识别**——通读，把文中的**事实**、**理由**、**结论**分别标出来
2. **判断**——画出实际的结构图：哪条支撑哪条，哪些是并列
3. **概括**——尝试用一句话概括全文中心思想。**概括不出来，就是最严重的发现**
4. **标题抽取测试**（强制）——把所有各级标题单独抽出来，连成一段读

### 标题抽取测试怎么做

把文中所有标题按出现顺序抄成一串，不带正文，然后只读这一串，回答：

- 能不能拿到**完整论证**（不只是"讲了哪些方面"，而是"在论证什么"）？
- 能不能拿到**中心思想**？

两个都能 → 标题合格。
只能拿到「讲了哪些方面」→ 标题是类别不是结论，命中反模式 7。
连方面都拿不到 → 严重，标题基本没承载信息。

**把抽取出来的那一串标题原样写进报告**，让用户自己看。这比你描述十句都有说服力。

---

## 数据自洽检查（强制，先于结构诊断）

**算术错误比结构问题更急。** 一份数据报告里的公式对不上，读者验算一次发现错了，
后面所有数字他都不会再信——这时候结构再完美也没用。

文中只要出现数字，逐项过一遍：

| 检查项 | 做法 |
|---|---|
| **公式验算** | 凡是写出了算式的，代入数字算一遍，对不上就记下来 |
| **重复数字比对** | 同一个数在文中出现两次以上，比对是否一致（正文写 3210、公式里写 3120 这类笔误） |
| **分项与总计** | 各分项之和是否等于写出的总计 |
| **百分比加总** | 声称穷尽的百分比是否加到 100% |
| **时间一致性** | 日期、周期、区间前后是否矛盾（如统计区间写明 41 天，公式里却按 30 天折算） |
| **单位一致性** | 同一指标是否混用了不同单位或口径 |

**只报「对不上」，不报「数字本身对不对」。** 你验证不了外部事实——
无法判断「上月活跃用户 12 万」是不是真的。但你能判断这个数在文中前后是否一致、
公式算不算得出写下的结果。守住这条边界。

结果写进报告的【数据自洽】段。全部通过就写「已验算 N 处公式，全部自洽」——
这句话本身对用户是有价值的。

## 八项反模式

逐条比对。每命中一项，记下原文片段。

### 反模式 1：空洞的类别句

**长相**：「该公司存在 3 个问题」「有以下几点体会」「主要包括三个方面」「相关情况如下」

**为什么是问题**：这些句子只声明了数量和类别，没有传递任何实质信息。
读者读完这一句，脑子里什么都没留下。

**改法**：把类别句替换成**实质结论**。
- ✗ 「该公司存在 3 个问题」
- ✓ 「该公司的问题集中在现金流：应收账期从 45 天拉长到 90 天，库存周转下降 40%，且新增授信被银行暂停」

**注意**：紧跟在带信息小标题前面的过渡句（「这一层做三件事」）危害较小，
不必当成主要问题列出。

---

### 反模式 2：结论被埋或缺失

**长相**：核心结论出现在第三段、最后一段（尤其是「结语」里），或者根本没出现。
开头是「众所周知」「近年来」「随着…的发展」，或者只有一句目录预告（「本文分上下两篇」）。

**为什么是问题**：读者（尤其是领导）通常只读前三行。结论在后面，等于没写。
**目录预告不是结论**——它告诉读者文章怎么排版，不告诉他结论是什么。

**改法**：把结论提到第一段第一句。如果结论写在结语里，直接把结语整段挪到开头。
前面那些铺垫，要么删掉，要么压缩进 SCQA 的 S。

**如果原文根本没有中心思想**：试着从材料里替他归纳一句，但必须**只用原文已有的信息**，
并注明「这句话完全来自你写的内容」。归纳得出来 → 说明材料够，只是少了归纳这一步。
归纳不出来 → 材料本身不支持任何结论，这是更严重的问题。

---

### 反模式 3：分组不 MECE

**长相**：同一层的几条之间有重叠，或者加起来明显有缺口，或者**维度不统一**。

- 重叠例：「① 线上推广 ② 搜索引擎投放 ③ 线下活动」——①②重叠
- 遗漏例：讲区域业绩只讲了华东华南，公司还有华北
- 维度不统一例：前四项是流程的四个阶段，第五项是贯穿全流程的横切关注点，
  五项并列 → 必然重叠

**一个强信号：作者自己打了补丁。** 文中出现「需要说明的是，这部分前面已经提过，
这里换个角度再看一次」这类解释，几乎总是分组维度有问题。
分组对了，不需要解释为什么重复。

**改法**：换一个分类维度重切；或用 2×2 矩阵重新划分；
或把横切项从并列层里拿出来，明确标成「贯穿各层的第 N 个维度」。

---

### 反模式 4：序言塞了读者不知道的信息

**长相**：SCQA 的 S（情景）里出现了读者不了解的项目代号、内部黑话、新概念、未公布的数据。

**为什么是问题**：S 的作用是建立共同起点。写了读者不知道的东西，
他会停下来想「这是什么」，注意力就跑了，后面的 C 和 A 全接不住。

**改法**：S 里只保留读者一定知道或一定会认同的事。必须交代的新信息，挪到正文。

**注意**：黑话是否算问题，取决于读者。周报给同组领导看，内部代号是共同语言，不算问题；
同一份材料要往上流转或跨部门发，就要加一句解释。判断前先确认读者。

---

### 反模式 5：同一组混用排序逻辑

**长相**：前两条按时间排（「上半年…下半年…」），第三条突然按结构排（「华东区…」）。
或者同一份文档里的几份清单，各用各的顺序。

**为什么是问题**：读者会试图找出这几条之间的规律，找不到就会觉得混乱，
即使他说不出为什么混乱。

**改法**：时间、结构、重要性，**同一组只用一种**。如果确实是两个维度，那说明应该拆成两组。
一份文档里多份平行清单，尽量用同一种顺序（给上级看的优先用重要性顺序）。

---

### 反模式 6：层级超载

**长相**：一层里并列 8 条、10 条；或者演绎推理链拉了 6-7 步。

**为什么是问题**：短期记忆装不下。超过 7 项读者就记不住，理想是 3-4 项。

**改法**：**上提一层做归并**——把 9 条归成 3 组，每组下面挂 3 条细项。
不是删掉几条了事。演绎链超过 4 步的，改用归纳。

---

### 反模式 7：无信息标题

**长相**：「背景」「介绍」「现状」「问题分析」「下一步计划」「结语」「数据概览」「本周进展」

**为什么是问题**：标题本该承载信息。全是这种标题，标题抽取测试必然不通过。
违反「证」的验收口径——「没时间只看标题就够了」做不到。

**改法**：把标题改写成带判断的句子。
- ✗ 「问题分析」 → ✓ 「流失集中在注册后 3 天内，占比 68%」
- ✗ 「下一步计划」 → ✓ 「建议 10 月起把新手引导从 4 步压回 2 步」
- ✗ 「本周进展」 → ✓ 「本周：A 模块上线 2 个渠道，B 功能排期已确认」

**常见的退化**：同一份文档里，前半部分的标题是「名称：结论」，
后半部分退化成只有「名称」。对比一下前后，退化处就是要改的地方。

---

### 反模式 8：平行结构不对称

**长相**：同一层的几个部分，内部结构不一样。

- 项目一有「数据 / 进展 / 计划」三节，项目二只有「进展 / 计划」两节
- 同一份文档里三份清单，用了三种不同的排序
- 前三章每章都有小结，第四章没有

**为什么是问题**：读者会用第一个部分建立预期，第二个部分对不上，就得重新适应。
而且**缺的那一格通常不是「没有」，是「忘了写」**——把它标出来，往往能帮作者发现遗漏。

**改法**：定一套小节结构，所有平行部分都用它。
某个部分确实没有某一格，写「本周无」，而不是省略。
多份平行清单统一用同一种排序。

## 输出格式（固定，顺序不变）

```
【场景判断】
属于「XXXX」，方向：自上而下 / 自下而上
读者：……（用户未说明时标注「（推断）」）

【总体判断】可直接发 / 局部调整 / 需动主干

【做得好的】
1. ……（引用原文 + 为什么这样做是对的）
2. ……
（1-3 条。确实没有就写「无特别之处」）

【数据自洽】
已验算 N 处公式：……
（全部通过就写「全部自洽」；有问题逐条列出，标明原文位置）

【中心思想】
原文的中心思想是：……
（或：原文没有明确的中心思想。从你的材料里能归纳出来的是：……，这句话完全来自你写的内容）

【序言检查】
S 情景：有 / 无；是否都是读者已知信息
C 冲突：有 / 无
Q 疑问：能否从 S+C 自然引出
A 回答：有 / 无；是否与中心思想一致

【问题清单】
1. 原文：「……」（直接引用）
   命中：反模式 X · 名称
   建议：……

【标题抽取测试】
抽出来的标题串：……
判定：通过 / 只能拿到方面 / 基本无信息

【修改优先级】
1. ……（改了收益最大的放第一）
```

## 输出规则

### 1. 三档判定按「改动成本」，不按问题类型

| 判定 | 口径 | 典型改动量 |
|---|---|---|
| **可直接发** | 无结构性问题，至多措辞可优化 | 0 |
| **局部调整** | 不动主干：补标题、补一句结论、调顺序、补齐缺的格子 | 15 分钟内改完 |
| **需动主干** | 中心思想缺失、需要重新分组、需要重排章节顺序 | 要先重搭骨架 |

**不要用问题类型机械对应判定。** 「结论写在结语里」听起来严重，
但如果修复方式只是把结语整段挪到开头，那就是**局部调整**，不是需动主干。
判定传达的是**用户要花多少力气**，不是问题有多"严重"。

判完之后加一句话说明改动量，别让用户被判定词吓到。

### 2. 每条问题必须引用原文

引不出原文的是主观感受，不写进清单。

### 3. 问题清单控制在 5 条以内

挑最值钱的说。列 15 条等于没列——用户不知道先改哪个。

### 4. 【做得好的】不是客套

**写得好就说好**，而且要说清楚**为什么这样做是对的**，不能只说「写得不错」。
确实找不到优点，就写「无特别之处」——硬夸比不夸更伤信任。

只报问题不报优点，是这类工具最招人烦的地方：一份水平明显高于平均的稿子，
读起来却像通篇挨批。

### 5. 只评结构与数据自洽，不评文风

用词老套、句子长，除非影响结构清晰度，否则不在评审范围内。
但**数据自洽属于评审范围**，而且优先级最高——见上面的数据自洽检查。
明显的错别字影响理解时（出现一个读者看不懂的生造词），可以一句带过，不展开。
