# 结构化写作

把职场文档搭成「结论先行、以上统下、归类分组、逻辑递进」的金字塔。核心主张：**先搭骨架，再下笔。**

方法论源自 Barbara Minto 的《金字塔原理》。本 skill 是把这套原理操作化成
AI agent 可执行的流程与检查表，不是原书复述。

---

## 第 0 步：先判断，不要直接动笔

每次触发都先做两个判断，把结论一句话告诉用户，再继续。

### 判断一：走哪个模式

| 用户在做什么 | 模式 | 读哪个文件 |
|---|---|---|
| 要一份还不存在的文档，或只给了素材/要点 | **写** | `references/write.md` |
| 给了现成稿子，问「怎么样」「有什么问题」「帮我看看」 | **审** | `references/audit.md` |
| 给了现成稿子，明确要求「改」「重写」「按金字塔重构」 | **改** | `references/revise.md` |

模式判断不清时，默认走**审**，并问一句「要我直接改，还是先指出问题你自己改？」
用户只是分享草稿、没提要求时，**默认走审**，不要擅自重写别人的文字。

### 判断二：是否走简版

内容短于 3 句话、或属于即时消息/简短邮件/群内通知时，**走简版**：
只套两条规则——**结论先行**（第一句就是结论）与**归类分组**（如有多项，不重不漏），
不做完整金字塔、不写 SCQA 序言、不出骨架确认环节。

给一份 3 行的消息套五步骤，是这套方法最常见的误用。

## 四条自检标准：论、证、类、比

这四条不是知识点，是**每次交付前逐条过一遍的清单**。任何模式的产出都必须过这四关。

| 字 | 标准 | 自检问法 | 对应反模式 |
|---|---|---|---|
| **论** | 结论先行 | 读者只看第一段，能不能拿到核心结论和要他做的事？ | 1、2 |
| **证** | 以上统下 | 每个下级要点，是不是都在回答上级抛出的那个问题？ | 4、7 |
| **类** | 归类分组 | 同层要点之间有没有重叠？加起来有没有遗漏？（MECE） | 3、6 |
| **比** | 逻辑递进 | 同一组要点是按同一种顺序排的吗？（时间 / 结构 / 重要性，三选一） | 5、8 |

**「证」的验收口径 —— 标题抽取测试**：把所有各级标题单独抽出来连成一段读。
读完能不能拿到完整论证？能，标题合格；不能，说明标题没承载信息，回去改。
**这是审模式的强制步骤**，见 `references/audit.md`。

## 写模式：先出骨架，停下来等确认

完整流程见 `references/write.md`。三条硬规则写在这里：

### 规则一：先出骨架，停下来等确认

**不要一次性吐出成稿。** 第一轮只输出骨架，格式固定：

```
【中心思想】一句话，必须是结论不是主题
【关键句】3-4 条，每条都是完整结论句
【序言 SCQA】情景 / 冲突 / 疑问 / 回答，各一到两句
【建议篇幅】约 N 字，M 个章节
```

然后明确问一句：「骨架对吗？要调整哪里？确认后我展开成稿。」
用户确认或提出修改后，才进入成稿。

例外：用户明确说「直接给我成稿」「不用确认」时，跳过这一步。

### 规则二：先问清目标，不要替用户猜

起草前至少确认两件事，缺一不可：

1. **读者是谁，以及看完之后你希望他做什么？**（目标不是「让他了解」，是具体行为——批预算、拍板方案、调资源）
2. **读者已经知道哪些背景？**（决定 SCQA 里的 S 写什么，写读者已知的事才不会让他出戏）

用户没说清就问，别用「一般来说」填空。

### 规则三：素材不够就标注，不要编

事实、数字、时间、人名，只能来自用户给的材料。
缺了就在骨架里写 `【待补：Q3 留存率具体数字】`，不要编一个看起来合理的数。

## 审模式：返回诊断，不返回新稿

完整流程、八项反模式与数据自洽检查见 `references/audit.md`。

**核心约束：审的时候不改写。** 用户看完说「按你说的改」，才切到改模式。

输出格式固定七段，顺序不变：

```
【场景判断】四类场景中的哪一类，方向是自上而下还是自下而上
【总体判断】可直接发 / 局部调整 / 需动主干   三选一，按改动成本判
【做得好的】写得对的地方，1-3 条。没有就写「无特别之处」
【数据自洽】公式验算、重复数字比对、分项与总计核对的结果
【中心思想】原文的中心思想是什么；找不到就直接说找不到
【序言检查】S/C/Q/A 四要素齐不齐，S 是不是读者已知的事
【问题清单】每条：引用原文片段 → 命中哪项反模式 → 建议怎么改
【修改优先级】按「改了收益最大」排序，不是按出现顺序
```

三条规则：
- **总体判断必须和问题清单一致**——清单里有三条动主干的问题，就不能判「可直接发」
- **每条问题必须引用原文**，引不出原文的是主观感受，不写进清单
- **【做得好的】不是客套**——写得好就说好，找不到优点就写「无特别之处」，不要硬夸

## 改模式：重构结构，不改文风

完整流程见 `references/revise.md`。

先按审模式跑一遍诊断（内部进行，不必全部输出），再重构。输出格式：

```
【改动说明】3-5 条，说清动了什么、为什么
【改后全文】
【改前改后对照】只列结构层面的关键改动，不逐字对照
```

**保留用户的语气和用词习惯。** 这套方法管的是结构，不是文风。
把一份口语化的周报改成公文腔，是越界。

## 四类职场写作场景

四类场景走的是**不同的流水线**，不是同一套流程换个说法。判断属于哪类，然后读
`references/scenarios.md` 里对应的那一节。

| 场景 | 典型文档 | 三个 STEP | 方向 |
|---|---|---|---|
| **清晰传递信息** | 通知、说明、方案介绍 | 设计标题 → 撰写序言 → 展开内容 | 自上而下 |
| **准确总结工作** | 周报、月报、述职、复盘 | 成果分类 → 排序整理 → 概括总结 | **自下而上** |
| **充分说服他人** | 立项、申请、提案 | 明确观点 → 疑问回答 → 逻辑归整 | 自上而下 |
| **有力汇报方案** | 完整方案、决策建议书 | 底层逻辑 → 五步骤展开 | 自上而下 |

**最容易做错的是第二类。** 「准确总结工作」必须**自下而上**——先把散落的成果罗列出来、
分类、再归纳出结论。一上来就定中心思想再往下填，会写成一份自我美化的空文。

这一类的高频失败是**第三步「概括总结」被整个跳过**：只罗列做了哪些事，不归纳出结论。
表现为通篇写「推进了 X」「开展了 Y」这类动作，而不是「X 做到了什么结果」。

## 不要触发的场景

遇到这些，明确说明这套方法不适用，然后按用户本来的需求正常处理：

- **叙事性文档**：事故时间线、会议纪要、访谈记录、操作手册、教程、分步指南——
  这些的顺序由事实或操作步骤决定，不该被重排成金字塔
- **参考手册类技术文档**：API 文档、配置项说明、参数表、代码注释——
  这些按字母序或模块组织，供查阅而非通读
- **创意与情感类**：公众号推文、文案、致谢信、慰问、道歉信
- **已经很短且结构清楚的内容**

**边界说明**：讲清「某个系统为什么这样设计」的技术说明文**适用**这套方法——
它有论点、有论据、要说服读者，跟参考手册不是一回事。
判断依据是「读者是通读还是查阅」：通读的适用，查阅的不适用。

对已经写得不错的稿子，说「结构没问题」就够了，不要为了显得有用而硬找问题。

## 全局硬规则

1. **不编造**。事实、数字、引语只能来自用户给的材料。缺失就标注 `【待补：...】`。
2. **先骨架后成稿**，除非用户明确豁免。
3. **审不改写**，改要说明改动理由。
4. **凡有公式必验算**。审模式必做数据自洽检查——算术错误比结构问题更急。
5. **同一组只用一种排序逻辑**，不能前两条按时间、第三条按重要性。
6. **单层不超过 7 项，理想 3-4 项**。超了就上提一层做归并。
7. **不替用户做决定**。目标、读者、口径这类事，问清楚再动笔。
